# 高频面试问答

## 1. 为什么测试项目要分层？

配置、HTTP 客户端、测试数据、数据库访问、断言和用例分开，目的是隔离变化。例如 API 地址变化只改配置，统一 header 或日志只改 ApiClient，用户生成规则只改 DataFactory。分层不是为了目录好看，而是减少重复和定位问题时的搜索范围。

## 2. 为什么 fixture 要区分 session 和 function？

登录 admin 和创建 SQLAlchemy Engine 在每个测试重做成本高、且不可变，适合 session。用户、工单和角色修改会互相影响，必须 function 级隔离。判断标准是资源是否会被测试修改，而不是“哪种 fixture 更高级”。

## 3. 如何隔离测试数据？

每次 DataFactory 生成随机 `run_id`，用户名、邮箱和工单标题都带唯一标识；真实 API 创建后记录 ID，先生成依赖数据；测试结束按审计事件、工单、用户的顺序清理。测试只对精确 ID 或本次唯一关键词统计，不依赖全库总数，也不依赖执行顺序。

## 4. 为什么不用数据库事务回滚？

API 和测试进程使用不同的数据库连接。测试进程开启事务并不能包裹 API 的写入，反而会制造“看起来隔离、实际没隔离”的假象。当前项目是黑盒 HTTP 集成测试，所以采用真实写入和 teardown 清理。

## 5. token 怎么管理？

每个用户对象持有独立的 ApiClient 和 token；登录后由客户端统一加 `Authorization: Bearer ...`。错误密码、无 token、畸形 token、过期 token、账号停用后的旧 token 分开测试。不会把 token 写死在代码里，也不会让多个用户共用一个可变 session header。

## 6. 为什么不能只校验状态码？

接口返回 200 不代表数据正确。例如状态码正常但 `assignee_id` 没落库、状态更新了但审计事件没生成、失败请求返回 409 但事务已经部分提交。项目会在写操作后用独立 SQL 查询精确 ID，验证字段、外键、事件数和失败前后不变。

## 7. 401、403、404、409、422 怎么区分？

- 401：没有身份、token 无效或已过期。
- 403：身份有效，但角色没有接口级权限。
- 404：资源不存在；对象级越权也返回 404，避免泄露资源是否存在。
- 409：身份和参数都合法，但与当前业务状态冲突，例如重复分配、非法状态流转。
- 422：请求结构或字段值未通过校验，例如非法枚举、显式 null、长度越界。

## 8. 状态机怎么测？

先验证合法链路 `open -> assigned -> in_progress -> resolved -> closed`，再验证高风险非法路径：跳过中间状态、重复提交当前状态、creator 代替 assignee 开始处理、非 creator 关闭、已开始后重新分配。每次失败不仅看 409，还回查 tickets 状态和 events 数量未变化。

## 9. 权限怎么测？

分垂直越权和水平越权。垂直越权是 employee 调 admin 接口，应返回 403；水平越权是两个同角色用户访问对方资源，应返回 404。还要覆盖同一资源上的不同动作：creator 能编辑 open 工单但不能再分配后编辑，assignee 能改状态但不能关闭，creator 能关闭但不能开始处理。

## 10. 失败后怎么定位？

先看请求方法、URL、payload、响应码和响应体，再看 API 日志和数据库实际状态。然后判断是产品缺陷、测试数据问题还是环境问题。用最小请求复现；如果响应失败但数据库不变，通常是前置校验；如果返回 500 或部分写入，优先查服务端异常和事务边界。

## 11. 怎么保证 CI 稳定？

固定 Python 3.12 和依赖锁；数据库、API 都有 healthcheck；测试前等待服务健康；每个测试独立数据并 teardown；失败上传 JUnit 和容器日志；连续执行检查偶发失败。CI 中不使用开发者本机状态，也不依赖固定 ID 或执行顺序。

## 12. 覆盖率怎么解释？

本项目没有把 pytest-cov 的数字冒充 FastAPI 服务覆盖率，因为测试和服务是不同进程。项目从需求覆盖、接口覆盖、风险覆盖和数据覆盖说明测试充分性，并列出未测试的并发、性能和安全范围。代码行覆盖率应当通过服务进程插桩单独测量。

## 13. 既然用了 requests，为什么还封装 ApiClient？

如果每个用例都手写 URL、header、超时和日志，修改接口地址或鉴权方式会产生大面积重复改动。ApiClient 统一这些细节，测试用例只表达业务动作。封装保持在薄层，不把断言藏进客户端，否则失败时很难看清期望。

## 14. 参数化会不会让用例虚假膨胀？

只有同一业务规则、不同等价输入才参数化，例如标题 1/120/121、page_size 0/1/100/101。项目实际有 95 个展开后的 testcase，其中参数化覆盖的是明确边界，不是把同一请求复制几十次。

## 15. 被测系统是自己写的，会不会自说自话？

README 已明确它是自建测试靶场，不冒充生产系统。项目价值是展示需求拆解、接口测试框架、权限/状态机设计、SQL 校验、缺陷定位和 CI。面试时要主动说明边界，并强调两个真实发现的缺陷和修复过程，而不是声称系统有真实用户量。

## 16. 你发现过什么缺陷？

一是工单更新显式传 null 时返回 500，原因是 optional Pydantic 字段允许 null，随后写入非空列触发 IntegrityError；修复为请求模型在 before validator 拒绝显式 null。二是管理员可以降级自己，可能造成管理权限锁死；修复为当前账号降级时返回 409，并用 SQL 验证角色未变化。

## 17. 以后如何扩展并发测试？

可以先用线程池并发给同一 open 工单分配不同技术员，验证只有一次成功且 `assignee_id` 唯一；再加数据库约束/版本号或行锁支撑。并发测试必须准备重复执行和延迟统计，不能只跑一次看到成功就宣称稳定。

## 18. 项目中还有哪些可以改进？

- 使用 Alembic 管理数据库迁移，替代启动时 `create_all`。
- 为 CI 建立独立测试数据库和更细的失败日志。
- 增加 OpenAPI schema 契约检查。
- 增加并发分配和并发状态更新测试。
- 在稳定后增加 Allure 趋势报告。
- 使用覆盖率插桩单独统计服务端代码覆盖率。
